# ترحيل قدرات الاختبار إلى المحادثة

التاريخ الأصلي: 2026-10-02. هذه وثيقة تخطيط تاريخية.
تنفيذ الخطة اللاحقة «جلسة واحدة» موثّق في `ONE_SESSION_CHECKPOINT.md` بتاريخ
2026-10-03. العمل محلي على `main`؛ الـMigration الجديدة لم تُطبّق على قاعدة العمل.
وصف «ما أثبته فحص الكود» أدناه يخص الحالة قبل التنفيذ، وليس التطبيق الحالي.

## النتيجة المطلوبة

جلسة واحدة داخل المشروع، تبدأ بالكتابة وتستمر بعد الاختبار. المساعد يفهم طلب
الكتابة أو التحليل أو الاختبار من الكلام وسياق المشروع. أدوات QA تظهر داخل
الجلسة عند الحاجة، والقرارات المطلوبة تظهر فوق الكاتب الحالي. لا زر Start test،
ولا اختيار Chat/QA، ولا صفحة مختلفة يشعر المستخدم أنه انتقل إليها.

يظل المستخدم قادرًا على المحادثة دون مشروع. عند طلب تجهيز اختبار، اختيار أو
إنشاء المشروع يكون داخل الجلسة مع حفظ المسودة. عرض ملفات المشروع والمتصفح
المرئي مستقبلًا يستعمل مساحة العمل نفسها؛ المتصفح المرئي خارج هذا التنفيذ.

## ما أثبته فحص الكود

- `App.vue` يعرض المحادثة وجلسة الاختبار عبر فرعين مختلفين. `handleStartTest`
  ينقل إلى `#/tests` ويمرّر المسودة. تفعيل محادثة محفوظة يحتفظ بمعرّفها ورسائلها.
- الكاتب ولوحة المشروع مشتركان، لكن عرض الرسائل وإدارة الإرسال مستقلان.
- تنسيق Markdown والجداول مرتبط بـ`.answer`؛ رسائل الاختبار لا تستخدم هذا
  الغلاف. رأس المحادثة يعرض `usageSummary`، ورأس الاختبار لا يعرضه.
- التفعيل يحذف المحادثة من قائمة Chat قبل اكتمال تحميل قائمة Tests. فشل قراءة
  قائمة Tests يفرّغها. هذان مساران قد يفسّران الاختفاء، ولم يُثبت بعد أنهما
  يفسّران كل حالة لاحظها المستخدم.
- نتائج الطلب والموافقات المنتهية تُرسم بعد جميع الرسائل، وليست مدمجة في
  تسلسل زمني معها. الرسائل المحفوظة تُقرأ حسب التاريخ ثم المعرّف؛ تعادل
  التواريخ، خصوصًا بعد الاستيراد، يحتاج ترتيبًا ثابتًا يحفظ ترتيب الأدوار.
- جلسات الاختبار تستخدم `Chat` و`Message` الموجودين، مع امتداد `TestSession`
  وسجلات QA مستقلة. لا يلزم نسخ تاريخ المستخدم إلى قاعدة أو منتج جديد.
- مسار المناقشة في Tests يعيد استخدام `createChatReply`، لكنه موجّه لتخطيط
  QA، ويعيد ردًا ومقترحًا. المسار العام يدعم فهم المهام، لكنه لا يمثل حاليًا
  طلب تشغيل متصفح أو صلاحية تنفيذ.

## القرارات المعمارية

1. **واجهة جلسة واحدة:** استخراج غلاف المحادثة والرأس وعرض الرسائل والكاتب
   ولوحة المشروع إلى مكونات مشتركة. عرض رسائل الاختبار يستخدم مكوّن الرسالة
   نفسه، مع عناصر منفصلة لأحداث النظام والأدلة والقرارات.
2. **هوية واحدة:** المشروع والمعرّف والعنوان والمسودة والمرفقات ثابتة طوال
   الرحلة. قدرات QA امتداد للجلسة. قيم `CONVERSATION/TEST` الحالية تبقى تفاصيل
   توافق داخلية أثناء الترحيل؛ لا ترحيل جماعي أو نسخ سجلات اعتمادًا على العنوان.
3. **إدارة جلسة واحدة:** واجهة حالة موحّدة للرسائل والحفظ والإرسال والأخطاء
   والمرفقات والاستخدام. تستدعي خدمات التخزين الحالية عبر adapters محددة؛
   لكل دور كاتب واحد للسجل. لا إرسال عبر Chat وTests معًا، ولا مزامنة Chat
   العامة فوق رسائل اختبارات يديرها السيرفر.
4. **قدرات بحسب الطلب:** نتيجة فهم الكلام تكون ردًا عاديًا أو سؤال توضيح أو
   مقترح اختبار منظّم. السياق يساعد الفهم؛ لا يبدأ تجهيزًا أو تشغيلًا بمجرده.
   اقتراح كتابة test cases أو شرح QA لا يعني طلب تشغيل المتصفح.
5. **العقود التنفيذية الحالية:** تجهيز المقترح بعد تأكيد نطاقه، وتشغيل Recipe
   بعد موافقة التنفيذ الدقيقة، واعتماد سجل QA بعد مراجعته. خدمات Runner وQA
   وREST/MCP الحالية تبقى المرجع لهذه الأفعال.

## ترتيب التنفيذ

### 1. توحيد العرض والقائمة

- إعادة استخدام الرأس وعرض الرسالة وMarkdown والكود والجداول والنسخ والتصدير
  والمرفقات في الجلسة العادية والجلسة التي تحتوي اختبارات.
- نقل بطاقة القرار و`QaRunApprovalPanel` و`TestRequestRecord` إلى مكونات قابلة
  للتركيب داخل المحادثة؛ الإقرار والنسخة وRunner وتأكيد الإنتاج تبقى بحالة
  واحدة، مع بقاء التفاصيل الموسّعة داخل السجل.
- بناء قائمة جلسات موحّدة للمشروع والسايدبار، keyed بالهوية الفعلية. أثناء
  تغير القدرات يبقى الصف موجودًا. فشل القراءة يعرض حالة إعادة محاولة ويحفظ
  الصفوف المحمّلة لنفس الحساب؛ تغيير الحساب يمسح بيانات المالك السابق فورًا.
- الروابط القديمة `#/tests` تفتح غلاف المحادثة نفسه وتحدد الطلب المطلوب.
  أسماء الروابط الداخلية ليست مطلوبًا تغييرها لإثبات توحيد الواجهة.

### 2. توحيد إدارة الأدوار وفهم المطلوب

- بناء منسّق جلسة يستعمل الحالة والمرفقات والمسودات الحالية، ويختار مسار
  الإرسال على السيرفر حسب إمكانات الجلسة والطلب، مع منع التكرار والإصدارات
  المتوقعة. التفعيل والحفظ الجاريان لا يفقدان الرسائل أو يعيدان فوترة دور.
- توسيع فهم النية الحالي بمقترح اختبار مضبوط البنية؛ ردود الكتابة والمناقشة
  تبقى طبيعية قبل الاختبار وبعده. لا يوجد تبديل وضع مطلوب من المستخدم.
- إزالة زر Start test بعد إكمال هذه الرحلة من النص إلى المقترح. إذا لزم
  تفعيل امتداد الجلسة داخليًا، يحتفظ بالهوية ولا يغيّر الصفحة أو المشروع.
- للمستخدم دون مشروع، يظهر اختيار المشروع عند تأكيد تجهيز المقترح؛ تظل
  المحادثة العامة والضيف مدعومتين وفق العقود الحالية.
- تحديث/إلغاء المقترح مرتبط برسالة المستخدم ونسخة الجلسة. طلب جديد بعد
  انتهاء اختبار ينشئ سجل QA جديدًا؛ المعاينة التاريخية لا تغيّر هدف الأوامر
  الجديدة بصمت. لا تشغيل متوازٍ في الجلسة ضمن هذه الجولة.
- الكريديت يعرض ملخص الاستخدام القانوني الحالي من خدمة usage المشتركة.
  يُحدّث بعد المحادثة وأعمال QA دون جمع أو خصم محلي مخمّن؛ الرد غير الحامل
  للرصيد لا يمسح المؤشر. توسيع response DTO يكون إضافيًا عند الحاجة.

### 3. ترتيب السجل والاستئناف

- دمج الرسائل وأحداث QA المحفوظة في عرض زمني واحد، باستخدام هوية الحدث
  وتاريخه الحقيقي وتسلسله الموجود. لا إنشاء رسائل إضافية بسبب تغيير العرض.
- ربط نتيجة الاختبار وقرار المراجعة بموقعهما في السجل، بحيث يأتي كلام
  المستخدم اللاحق بعدهما. حالة القرار المعلّق تظل عند الكاتب وسهلة الوصول.
- تثبيت ترتيب أدوار الرسائل عند تساوي التواريخ. فحص الحفظ والاستيراد أولًا؛
  إذا احتاجت البيانات ترتيبًا مستمرًا إضافيًا، يُضاف تغيير schema محدود
  ومتوافق ويُختبر على قاعدة معزولة. لا اختلاق تواريخ للبيانات القديمة.
- تثبيت مصادر السياق للطلب المؤكد، والحفاظ على RAG والتعليمات والميموري
  والملفات والسياق التنفيذي القديم. تعديل المشروع الحالي لا يعيد كتابة snapshot.
- العودة والتحديث وانقطاع المزود والسيرفر يستعيدان الجلسة والعمل المسجّل؛
  لا تجهيز أو تنفيذ أو موافقة تلقائية نتيجة التنقّل أو إعادة المحاولة.

### 4. تنظيف العرض القديم بعد إثبات التوافق

- إزالة فرع عرض `TestSessionPage` المستقل بعد استعمال الغلاف المشترك فعليًا.
- إزالة زر التفعيل و`TestDraftHandoff` ومعالجات نقل المسودة القديمة بعد
  اعتماد المصدر الواحد. تبقى نقطة التفعيل الخلفية للتوافق ما دامت مستخدمة.
- إزالة CSS والأسماء والترجمات والاختبارات الخاصة بالواجهة الملغاة عندما
  لا تبقى لها مراجع. اختبار سلوك المستخدم يحل محل اختبارات شكل الواجهة القديمة.
- الإبقاء على الخدمات وسجلات التنفيذ والأدلة والموافقات وتوافق الروابط.
  حذف خدمات backend أو الجداول ليس جزءًا من تنظيف هذه الواجهة.
- تحديث وثائق التسليم وخريطة الحفاظ على الوظائف، مع تسمية الخطط السابقة
  تاريخية وتوضيح المنفّذ وحدود التحقق الفعلية.

## معايير قبول محددة

- جلسة داخل مشروع، بجدول وكود وصور ومرفقات: اطلب اختبارًا ثم اكتب تقريرًا
  بعد نتائجه. يبقى العنوان والمعرّف والمشروع وتنسيق الرسائل ومؤشر الاستخدام.
- لا يختفي صف الجلسة أثناء التفعيل أو بطء/فشل قراءة القائمة. العودة والتحديث
  والروابط القديمة تفتح الجلسة نفسها دون نسخ أو فقد المسودة.
- "اكتب test cases" و"فسّر نتيجة الاختبار" لا ينشئان تشغيلًا. الهدف الغامض
  يستدعي توضيحًا؛ الهدف المحدد يعرض مقترحًا؛ التنفيذ يستعمل موافقته الدقيقة.
- نتائج ومراجعات محفوظة بين رسائل قديمة وجديدة تظهر بالتسلسل الصحيح، حتى
  مع تعادل التواريخ. لا مضاعفة للأحداث بسبب تحديث العرض.
- الحفاظ على المهام الست والرفع واللصق والسحب والإفلات والنسخ والتصدير
  والاستيراد والأرشفة وتعليمات وميموري وملفات المشروع. استيراد المحادثة يعيد
  نصًا غير تنفيذي؛ العمليات المرتبطة بسجلات QA تحتفظ بقيود الحذف والنقل.
- اختبار الحسابات والمشاريع المنفصلة، الاستجابات المتأخرة، تكرار الإرسال،
  انتهاء الجلسة، الاستئناف، تغيير Recipe/Runner/الإصدار، وتأكيد الإنتاج.
- مراجعة بصرية للجداول والكريديت والتسلسل والقرار في en/ar/de والثيمين،
  1440/1024/992/991/390/320px والهواتف القصيرة، مع فحص السكرول الأصلي.
- فحوص الأنواع والترجمات والاختبارات والبناء، واختبارات متصفح ببيانات
  معزولة. عند تعديل backend/schema: اختبارات API وقاعدة معزولة كذلك.

## حدود التسليم

لا نشر أو commit/push أو تعديل لسجل QA الحقيقي المعتمد ضمن التنفيذ.
تطبيق migration، إن احتاجت الخطة التفصيلية واحدة، على قاعدة العمل خطوة
منفصلة تتطلب موافقة المالك على التغيير المحدد. لا بث متصفح أو تابات جديدة
أو Android أو مزود جديد أو Jira/Figma/MR أو MCP جديد في هذا الترحيل.

هذه وثيقة اتجاه وخطة ترحيل؛ تفاصيل DTOs وترتيب الرسائل تُحسم بفحص العقود
واختبارات إعادة الإنتاج في بداية التنفيذ، قبل إزالة المسارات القديمة.
